# ADR-003: 为什么 Runtime Loop 演进为 Graph 编排

## 状态
已通过 (Accepted)

## 日期
2026-09-24

## 1. 背景 (Context)

在第一代自主智能体设计中，“Runtime Loop”是事实上的标准范式（如早期的 AutoGPT、BabyAGI 以及自研第一代 Agent）。其核心是一个命令式的 `while` 循环：
```python
while not finished:
    thought = reason(history)
    action = plan(thought)
    observation = act(action)
    history.append((thought, action, observation))
```

这种模式在简单的线性任务（Linear Task）中直观且易于上手。然而，随着智能体应用场景从“演示 Demo”迈向“企业级生产”，Runtime Loop 遭遇了架构瓶颈：
1. **拓扑能力的局限**: 真实业务并非单一死循环，往往包含多路径跳转、失败回滚、动态重试、双智能体辩论与仲裁。在 `while` 循环中用嵌套 `if-else` 实现这些拓扑，代码迅速腐化为无法维护的面条式状态机。
2. **状态更新与计算混杂**: 循环体直接修改共享上下文，缺乏事务性隔离，导致很难追踪到底哪一次计算污染了状态。
3. **缺乏状态持久化边界**: `while` 循环中的调用栈驻留在进程内存中。一旦需要等待人类审批数小时甚至数天，或者希望系统崩溃后从断点无损恢复，命令式循环完全无能为力。

---

## 2. 决策 (Decision)

我们决定在 **AgentGraph** 项目中，将命令式的 **Runtime Loop** 彻底重构演进为声明式的 **Graph Orchestration（图编排架构）**：
1. **控制流抽象为有向图**:
   - 计算步骤抽象为图节点（Nodes）。
   - 执行转移抽象为图连线（Edges）与条件路由（Conditional Edges）。
   - 执行过程从“连续的命令式执行”转变为“离散的超步（Superstep）调度”。
2. **状态与计算彻底解耦**:
   - 节点只接受状态快照输入并产出状态增量输出，不就地修改全局状态。
   - 图引擎在超步边界统一执行状态规约（Reducer），保障数据演进的原子性与不可变性。
3. **天然形成持久化与中断边界**:
   - 超步与超步之间的间隙（Inter-step boundary）成为天然的检查点（Checkpoint）写入点与人机中断挂起点。

---

## 3. 影响 (Consequences)

### 正面影响
- **图结构即文档与架构**: 整个系统的流转逻辑清晰地映射在图拓扑中，可被静态解析、校验与可视化呈现。
- **高阶模式自然原生表达**:
  - 条件分支、回环重试只需增加一条有向边。
  - 并发执行（Fan-out / Fan-in）只需增加并行边。
  - 分层多智能体只需将一个完整图作为子图（Subgraph）嵌入节点。
- **天然的微服务与云原生亲和度**: 图在每个超步后都可以持久化到数据库中并彻底释放工作进程，极度适合无服务器（Serverless）和水平伸缩架构。

### 负面影响 / 挑战
- **思维模式转换**: 必须打破“从上到下按行执行”的传统命令式编程惯性，学会以“状态流经节点”的响应式思维设计代码。
- **单步开销微量增加**: 框架在节点执行之间进行状态克隆、快照持久化和边计算，带来轻微的毫秒级运行时开销（但在 LLM 秒级推理耗时面前可完全忽略不计）。

---

## 4. 未来可能变化 (Future Possibilities)

- 未来当工作流演进至超大规模（如上百个智能体节点并发协作）时，由于控制流已经完全图化，底层的执行器可以平滑无缝地从单机内存调度迁移至基于分布式消息队列（如 Redis Streams、Temporal 或 Kafka）的分布式执行引擎。
